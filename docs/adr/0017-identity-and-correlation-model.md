# 0017. Identity and correlation model

Status: **accepted, 24 November 2026**. Built in M11 prompt 3. Evidence for gates G2 and G3 is in `docs/gates/M11-gates.md`.

> **Amended by ADR 0018.** Route authorisation in decision 5 is now team-scoped: the three app roles remain, but a route is allowed by the caller's role in the team the request is about (Admin sees every team). Identity, approval records and correlation are unchanged.

## Context

Until now an approval was a display name: the portal asked a person to type one, and the Teams card action used `Activity.From.Name`. The Azure DevOps comment said "Approved by Dana", but nothing proved Dana was Dana, nothing tied the decision to what was proposed, and a write could not be followed back to the meeting that produced it. Chat commands also decided who was the Scrum Master from a list of names.

## Decisions

1. **Every actor is an Entra identity.** `ActorIdentity { ObjectId, TenantId, DisplayName, UserPrincipalName?, Source (Teams | Portal | Copilot | Agent), AuthenticationMethod }` is a Domain value object. `ActorIdentity.Create` refuses a missing or empty object id or tenant, so a name alone is not an identity. `FollowUp.Approve` and `Reject` take an `ActorIdentity`. `ApprovedBy` is derived text (the identity's display name).
2. **Legacy data loads unchanged and is never written again.** A stored follow-up with an approver name but no identity shows `unverified (legacy)`. `GetApprovedChanges` refuses it (`identity.legacy_unverified`), and a null identity cannot approve.
3. **Authority is a pure Domain rule** (`ApprovalAuthority`), applied in the handler through one `ApprovalGate`, so no adapter can skip it. The tenant must equal the deployment's tenant. Portal: the validated token must carry `Zava.Scrum.Approver`. Teams: the object id must be a configured administrator (`Identity:AdminObjectIds`), or the roster member (matched by `EntraObjectId`) the follow-up is for; Scrum Master items (plans, calendars, packs) are administrator only. Display names are never consulted. This replaces `Team:ScrumMasters` (a list of names) with `Identity:AdminObjectIds`.
4. **Roster correlation.** `Member.EntraObjectId` is resolved once from the mapped user principal name through Microsoft Graph (`User.Read.All` application permission, granted to the managed identity by `entra-post.ps1`), stored, and re-verified when a session is prepared; a changed answer replaces the stored id, an unreachable directory leaves it. A member with no account (a demo cast member) has none and cannot approve in Teams.
5. **Portal API validates tokens in the app.** A `Portal` JwtBearer scheme checks signature, issuer, audience (`clientId` or `api://clientId`), lifetime, `tid` equal to the tenant and a valid `oid`. Easy Auth headers (`X-MS-CLIENT-PRINCIPAL*`) are never read, and a test proves a request carrying them is refused. Three app roles on the portal app registration (`infra/entra/portal-app-roles.json`): `Zava.Scrum.Admin` (operate), `Zava.Scrum.Approver` (decide), `Zava.Scrum.Reader` (read, including the audit chain). Every `/api` route sits in one group: reader for reads, admin for anything that changes state, approver for approve and reject routes. A test enumerates every route and asserts this. The bridge websocket keeps its own session-bound token; `/healthz`, `/api/messages` (Bot Service token) and `/portal-config.json` (public client id and tenant) sit outside the group.
6. **Local runs.** With no `Portal:ClientId` the API registers a fixed local principal holding every role, only in the Development environment. Outside Development it registers a handler that authenticates nobody, so the API stays up and every portal call is 401 until the deployment sets the client id. The `Development` principal carries the tenant of `Azure:TenantId`, so approvals work locally when that is set.
7. **Approval trail.** `ApprovalRecord` is append-only: id, correlation id, follow-up id, team id, kind (Approved | Rejected | Applied), SHA-256 `ProposalHash` of the canonical proposed changes, the `ActorIdentity`, channel, timestamp, the claims that proved the sign-in (no tokens), and, on an `Applied` record, the id of the decision it follows and the Azure DevOps revisions. The write is a second record, never an update. Cosmos container `ApprovalRecords` (partition `/correlationId`) is written only with `CreateItem`, and the managed identity has a custom data-plane role there with create and read only (Bicep), so the platform, not just the code, prevents replacement. The local store is a JSON-lines file with no rewrite. The demo reset does not touch it.
8. **The write is gated on the trail.** `ApplyApprovedChangesHandler` refuses unless an `Approved` record exists whose hash equals the follow-up's current proposal hash, and appends the `Applied` record with the revisions the writer returned (`IWorkItemWriter` now returns `WorkItemRevision`). A proposal changed after approval is therefore refused.
9. **Correlation.** The session gets a W3C trace id (32 hex) when it is created. Follow-ups, approval records, the Azure DevOps change (`ApprovedChange.CorrelationId`), the outbox cards (`TeamsMessage.CorrelationId`) and the voice gateway's log scope carry it. Every attribution, and so every Azure DevOps comment the agent writes, ends with `Correlation: zsa-<first 12 characters>`. Sessions and follow-ups saved before this derive a stable id from the session id. `GET /api/audit/{correlationId}` (reader) accepts the full id or the `zsa-` tag and returns the session, its events, the proposals with hashes, the records, the cards and a `missing` list; the chain is complete when every decided follow-up has a matching decision record and every applied one has a write record with a revision.

## Not done, and why

- **Author attribution in Azure DevOps** (the revision author is still the managed identity) is prompt 5. The comment names the approver and carries the correlation tag; the revision history does not yet show the approver as author.
- **Team-scoped roles** (TeamLead, Member, Reader per team) are prompt 3A. Roles are app-wide. Records carry the team id so that check can be added without migrating them.
- **Display names are still used for presence**: the bridge matches a person who joins a meeting to a roster member by name to start the standup. That decides who is in the room, not who may approve; nothing is written because of it.
- **Teams tenant.** The tenant comes from the activity's conversation (or channel data). The Bot Service token is validated before the activity reaches the bot, but the tenant field itself is Teams' assertion, not a separate claim we verify.
- **Roster resolution runs at session preparation**, not at `StartStandup`.
- **Plan and calendar decisions** are authorised and attributed to the identity but only follow-up decisions (including the Scrum Master follow-up a plan creates) leave an approval record; a calendar approval creates meetings, not Azure DevOps changes.

## Consequences

- The portal no longer asks for a name; "Deciding as" shows the signed-in account, and the API ignores any name in a request body.
- The portal reads the live state with `fetch`, not `EventSource`, because `EventSource` cannot send the bearer token.
- Two infrastructure values are ids produced by hooks, not secrets: `PORTAL_CLIENT_ID` and `ADMIN_OBJECT_ID`. Bicep takes them as optional parameters and `entra-post.ps1` applies them again, so a fresh `azd up` works whichever order azd resolves them.
- Existing environments need the app roles assigned (the hook gives the administrator all three) and `Identity:AdminObjectIds` set.
