# 0018. Multi-team model and isolation

Status: **accepted, 25 November 2026**. Built in M11 prompt 3A. Evidence for gate G9 is in `docs/gates/M11-gates.md`.

## Context

The product served one team. The team id was a configuration value on the bot (`Team:Id`) and a constant in the portal, the Azure DevOps organisation was one global setting, every Teams conversation received every card, and the scheduler read one schedule. Prompt 3A makes one deployed agent serve every scrum team, in more than one Azure DevOps organisation, without any team seeing another's data.

## Decisions

1. **A team registry.** `Team` gains `Status` (Draft, Active, Paused, Archived), `TeamsBindings` (tenant, Teams team, channel or chat, purpose Recap | Standup | Planning), `Ceremonies` flags, `KnowledgeBaseIds` and `WorkSignalsEnabled` (both reserved, empty and off) and an optional `EntraGroupId`. Every new field is optional, so a stored team with none of them loads as Active with defaults. Archive is the only delete. `POST /api/teams` creates a Draft; a team runs ceremonies only when Active.
2. **Azure DevOps per organisation.** `IAdoClientFactory` keeps one `HttpClient` and credential per organisation, created lazily and cached by the normalised URL. The URL must be `https://dev.azure.com/{name}` or `https://{name}.visualstudio.com`, so a team cannot aim the API and its token at another host. `Ado:Org` is only the seed default. Reads and the connection test use the managed identity (ADR 0015 S4). Writes still use the managed identity because the approver's delegated token belongs to prompt 5; that is not built here.
3. **A cross-tenant organisation is refused.** The organisation's tenant is read from the `X-VSS-ResourceTenant` response header of an anonymous request to the organisation. It must equal the deployment's tenant, or registration fails with `team.org_other_tenant` ("a managed identity from another tenant cannot be added to the organisation"); an unreadable tenant is refused too. **Measured, not documented:** I observed the header live against the sandbox organisation (it returned the tenant id), but no Microsoft Learn page states it, so it is marked `VERIFY` in code. If it disappears, registration fails closed.
4. **A write is scoped to the team's project and area path.** `WorkItemScope` is a pure Domain rule. `ApplyApprovedChangesHandler` reads each item's location (`IWorkItemScopeReader`) and refuses the whole change set with `team.work_item_out_of_scope` before any write if one item is outside the team's project and area path (or a new item targets another project's iteration). Tests cover the rule and the refusal through the real mediator.
5. **One resolver for every entry point.** `ITeamResolver` is used by the portal (an explicit team id checked against the caller's memberships), the Teams bot (conversation to team through the bindings; an unbound conversation gets an onboarding card and nothing else happens), Copilot (the user's teams; more than one means ask, never guess), the scheduler and the media bot (the team id on the session). A request that resolves to no team, or one the caller cannot reach, is refused and logged. `Team:Id` is removed from the bot and the portal constant is gone.
6. **Authorization is team-scoped and server side.** Roles: Admin (the Entra app role `Zava.Scrum.Admin`; all teams and the registry), TeamLead (approve, schedule, edit prompts and behaviours for their teams), Member and Reader (read their team). Memberships are stored by Entra object id (over `ICollectionStore`, so a JSON file locally and Cosmos when deployed) and managed by an Admin or a TeamLead, with an add-only sync from an Entra group (Graph `GroupMember.Read.All`, granted to the managed identity by `entra-post.ps1`). `TeamAccess.Authorise` is a pure rule. A `TeamAuthorizationFilter` on the whole `/api` group works out the team of every request (route value, query, bound body, or the team of the session, follow-up, plan, calendar or audit chain the id names) and asks the resolver. A route that names no team and is not marked team-free is refused, so a new route is closed by default. **A team the caller is not in is answered 404**, as if it did not exist, so existence is not disclosed; a team the caller is in but may not act on is 403. The Approver app role from ADR 0017 still approves for a team the caller belongs to.
7. **The registry is Admin only; a lead edits settings, not the connection.** `PUT /api/teams/{id}` changes the connection, ceremonies, bindings and status and needs Admin. `PUT /api/teams/{id}/settings` (a lead) cannot change the Azure DevOps fields, which prevents a lead pointing their team at another team's project or area.
8. **Cards go only to the team's bound conversations.** `CardRouting` selects from the team's bindings by purpose; a team with none gets no Teams delivery (the card stays in the outbox). Previously every stored conversation received every card.
9. **Prompts resolve team override, then deployment override, then the default file.** The Prompts page edits only the selected team's override and shows which version is in effect.
10. **The scheduler runs per team in its own time zone, through a capacity governor.** `CapacityGovernor` is a pure Domain rule: a limit on concurrent standups per host (default 3), a stagger between starts (5 s) and a grace (10 min) after which a blocked standup notifies the team's recap channel. The reason a standup waits is stored on the schedule and shown. A ceremony is never dropped silently. The limit comes from `Capacity` options; realtime model and media bot capacity are the same limit by another name until a second constraint is measured.
11. **Every record carries the team id.** `LoggingBehavior` puts `TeamId` on the log scope and the span (`team.id`) and records `zava.scrum.usecase.duration` with `team.id` and the use case. The voice gateway's scope carries `TeamId`. `GateRunner` stores the team on each run and `--only-team` filters the summary.
12. **Demo seed.** Three teams (Payments, Identity, Catalogue), one Azure DevOps project each in the same organisation, with distinct rosters, goals and time zones. `SeedAdo` seeds all three by default and `--payments-only` seeds one; `Demo:PaymentsOnly` registers only Payments in the API, for the film.

## Measured (G9, westus3, `zavaw3`, build c3083b7)

Three Simulated Room standups ran at once for three teams: all completed in 379 s, 36 timed turns, total p50 3400 ms and p95 4919 ms, against a single-standup p50 of 3439 ms in the same environment. The audit chain was complete for all three. Ten teams were not run live; realtime quota in westus3 is 5 per model, and three standups already prove the concurrency path. The quota request for ten is recorded in `docs/gates/M11-gates.md` and is for the owner to file.

## Consequences

- Adding a team is configuration, not a deployment. Adding an Azure DevOps organisation is a **human gate**: the API's managed identity must be added as a user in that organisation (`docs/DEPLOY.md`).
- The isolation matrix (`PortalAuthorizationTests`) aims every route family at team B as a team A member, as a stranger and as an Admin. A test enumerates every `/api` route and fails if one is not classified.
- Not verified live: a second Azure DevOps organisation, the demo seed in Azure DevOps (`SeedAdo` was not run), the onboarding card in a real Teams channel, and the Entra group sync.
- `PROD:` Cosmos team and membership stores behind the same ports; the capacity limit per realtime model; delegated writes (prompt 5).
